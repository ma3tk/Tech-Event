# 通報・違反通知 (report-flag.md)

connpass の通知フロー、ガイドライン違反対応、ブラックリスト機能などについての調査。

## 1. 機能の目的

connpass の通報・違反通知機能は、プラットフォーム上で発生したガイドライン違反 (スパム、ハラスメント、誤情報、不適切なイベント、なりすまし等) を運営と主催者に通知し、適切な対処を促すことを目的とする。

- 健全なコミュニティ運営の維持
- ハラスメント被害者の安全確保
- スパム / 商用乱用 / 釣りイベントの排除
- 主催者・参加者双方への抑止力

connpass 公式は「イベント参加者向け」「イベント主催者向け」の 2 種類のガイドラインを公開しており、両者の役割分担を明確化している。

公式の説明 (要旨):
- connpass ページ内での違反 → connpass へのお問い合わせより通知。
- イベント会場内での違反 → イベント主催者に速やかに通知。
- 違反者に対し事実確認を行い、利用規約に基づきアカウントの削除を行うなど厳正に対処。

## 2. 利用シナリオ

| シナリオ | 経路 |
|----------|------|
| イベント説明文が他サイトのコピペ・スパム | connpass お問い合わせフォーム |
| 参加者プロフィールが露骨な広告・なりすまし | connpass お問い合わせフォーム |
| 当日会場で参加者によるハラスメント | 主催者にその場で通知 → 主催者が事実確認 |
| 主催者自身が違反 (差別的発言、不適切勧誘) | connpass お問い合わせフォーム |
| 個人情報の無断公開 (写真・氏名) | お問い合わせ + 必要なら警察 |
| 詐欺イベント (架空イベントでの集金) | お問い合わせ + PayPal への通知 |
| 参加者の度重なる無断キャンセル | 主催者がブラックリストに追加 |

## 3. 関連エンティティ・フィールド

```
Flag (推定構造)
├─ id
├─ flagger_user_id (nullable: 未ログインでも可能性)
├─ target_type: enum {event, group, user, presentation, comment}
├─ target_id
├─ category: enum {spam, harassment, fraud, copyright, impersonation, off_topic, other}
├─ description: text
├─ evidence_urls: [string]
├─ status: enum {pending, under_review, resolved_action_taken, resolved_no_action, rejected}
├─ assigned_moderator_id
├─ created_at, resolved_at
└─ resolution_note: text (運営内部メモ)

Blacklist (主催者用)
├─ group_id
├─ user_id (ブロック対象)
├─ reason: text
├─ added_by_user_id
└─ created_at
```

主催者単位の「グループブラックリスト機能」は公式に明記されており、参加申込を制限できる。

## 4. UI 上の入口と画面

### 4.1 通知

- 専用の通知ボタンは UI に明確に存在しない (各ページに「通知」ボタンが汎用配置されているわけではない)
- 通知経路は `https://connpass.com/inquiry/` の汎用問い合わせフォーム経由
  - 自由記述欄に「対象 URL」「違反内容」を書く運用
- イベント詳細 / グループ詳細にも個別の「通知」UI ボタンは確認できず、お問い合わせ導線へ誘導

### 4.2 主催者ガイドライン参照

- `/term/guideline` (ヘルプ) にてガイドラインと対応フローを掲載

### 4.3 ブラックリスト

- グループ管理画面の「ブラックリスト」機能
- 特定ユーザーの参加申込を恒久的にブロック
- 主催者間で共有はされない (グループ単位)

## 5. 外部サービス連携

通知フローは connpass 内部完結。外部連携が必要になるケース:

- 犯罪性のある案件: connpass → 警察 / 弁護士相談
- 決済関連の詐欺: PayPal 側の Resolution Center へ並行通知
- 著作権侵害: 著作権者から DMCA / 著作権法に基づく削除請求書を connpass へ提出
- 個人情報漏洩: 個人情報保護委員会への通知 (connpass 運営の義務)

API での通知受付は提供されていない。

## 6. ルール・制約

- 通知は匿名化されるが、運営内部では通知者のアカウント情報を保持 (悪意の連続通知を抑止)
- 主催者が同じ違反者を 1 グループから締め出しても、別グループや別アカウントでの再参加は防げない (= 抜本的解決にはアカウント停止が必要)
- ガイドライン違反のうち「軽微なもの」は主催者対応に委ねる方針 (= 運営が一律に介入しない)
- 通知内容は基本的に対象者には開示されない (個別事実確認時にプライバシーに配慮)
- 主催者にはまず「通知者の許可を得たうえで事実確認」「再発防止のための指導」「改善なければブラックリスト」というステップが推奨

## 7. 模倣実装時の代替案

### 7.1 通知 UI の明示化

connpass は専用通知 UI を持たず汎用お問い合わせ任せだが、模倣実装ではユーザビリティ向上のため専用の通知モーダルを全リソースに配置:

```
[...] メニュー
├─ シェア
├─ ブックマーク
└─ 違反を通知
    └─ カテゴリ選択 + 自由記述 + スクリーンショット添付 (任意)
```

### 7.2 通知カテゴリの設計

| カテゴリ | 詳細 |
|----------|------|
| spam (スパム / 過剰宣伝) | 同一内容の連続投稿、外部商用への誘導 |
| harassment (ハラスメント) | 個人攻撃、差別的言動 |
| fraud (詐欺) | 架空イベントでの集金 |
| copyright (著作権侵害) | 無断転載スライド |
| impersonation (なりすまし) | 別人を名乗るアカウント |
| inappropriate_content (不適切) | 暴力 / 性的 / 違法 |
| other | 自由記述 |

### 7.3 トリアージとモデレーション

- pending → assigned → under_review → resolved のステータス遷移
- モデレーター用ダッシュボード (Retool / 自作管理画面)
- SLA: 重大度 high (詐欺・ハラスメント) は 24h 以内に一次対応、それ以外は 72h
- 機械的トリアージ: NG ワード辞書 + LLM (Claude / GPT) でカテゴリ自動分類 → 人間レビュー

### 7.4 ブラックリストの強化

- グループ単位 (connpass 同等) + プラットフォーム全体 (Permanent Ban) の 2 層
- 主催者間で「警告フラグ」を共有する仕組み (個人情報を出さず "received_count" のみを表示)
- ブラックリスト対象者がメールアドレス変更で再登録するのを防ぐため、メールアドレス + 端末 fingerprint + IP の 3 軸で同一人物推定

### 7.5 監査ログとプライバシー

- 通知処理の全アクション (誰がいつ何を見たか) を audit log に記録
- 対象者のプライバシー保護: 通知内容と個人情報は最小権限で閲覧
- 通知者保護: 主催者 / 対象者には通知者の個人情報を渡さない

### 7.6 自動化 (LLM 補助)

- 通知内容を LLM で要約し、運営側の一次トリアージを高速化
- 似た通知の自動グルーピング (同一イベント / 同一ユーザーに対する複数通知)
- ただし最終判断は人間が行う (誤判定のリスク回避)

### 7.7 ガイドライン文書

- 法的根拠を明示 (利用規約の該当条項を引用)
- 多言語対応 (国際カンファレンス向け)
- 主催者向けに「ハラスメント対応マニュアル」テンプレートを配布
- Code of Conduct テンプレート (Berlin Code of Conduct、Contributor Covenant 等) の提供

### 7.8 反発対策

- 通知者を特定して退会させる「通知者狩り」を防ぐため、運営は通知者情報を厳重管理
- 主催者による「特定ユーザーへの嫌がらせ的ブラックリスト追加」も通知対象として受け付ける

### 7.9 透明性データ

- 半期ごとに「通知件数 / カテゴリ別内訳 / 対応結果」を匿名化して公表
- プラットフォームへの信頼を高め、通知者に対し「通知は無駄にならない」というメッセージを送る
