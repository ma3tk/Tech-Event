# connpass のアクセシビリティ評価

connpass.com を観察し、WCAG 2.1 AA 基準に照らしてアクセシビリティの観点を整理する。観察は公開ページ (トップ, /explore/, 各グループページ, ヘルプセンター) を対象とした目視と推測に基づく。

---

## 1. WCAG 4 原則からの評価

WCAG は 4 つの原則 (Perceivable / Operable / Understandable / Robust) で構成される。

### 1.1 Perceivable (知覚可能)

| 観点 | 現状の評価 | 改善余地 |
|---|---|---|
| テキスト代替 | カバー画像に alt 属性は付いていそうだが、装飾画像との区別が曖昧 | alt=""の徹底 |
| 時間ベースメディア | 動画は基本外部 (YouTube) なので connpass 自身の責務は薄い | キャプション要求のガイドライン整備 |
| 適応 | レスポンシブで折り返し対応あり | 縦書きや音声読み上げ順序を明示 |
| 識別可能 | 主要テキストはコントラスト比が確保されている印象 | グレー系ヘルパーテキストが薄い場合あり |

### 1.2 Operable (操作可能)

| 観点 | 現状の評価 | 改善余地 |
|---|---|---|
| キーボード | 基本フォームは Tab で辿れる | ドロップダウンメニューのフォーカストラップ要確認 |
| 十分な時間 | 申込フォームにタイムアウトはないと推測 | 抽選結果待ちの自動ログアウト時間の通知 |
| 発作と物理的反応 | アニメーションは控えめ | prefers-reduced-motion 対応の徹底 |
| ナビゲーション | サブドメイン構造でグループごとに区切られ整理 | スキップリンク (本文へジャンプ) 配置 |

### 1.3 Understandable (理解可能)

| 観点 | 現状の評価 | 改善余地 |
|---|---|---|
| 読みやすさ | 日本語のみ。lang="ja" 明示推奨 | 専門用語のグロッサリー |
| 予測可能 | 申込ボタン状態が多岐にわたるがラベルで明示 | 状態変化のアナウンス |
| 入力支援 | フォームエラーをインラインで表示する想定 | エラーサマリのスキップ実装 |

### 1.4 Robust (堅牢性)

| 観点 | 現状の評価 | 改善余地 |
|---|---|---|
| 互換性 | 主要ブラウザ対応 | スクリーンリーダ (NVDA, JAWS, VoiceOver) でのテスト記録公開 |

## 2. キーボードナビゲーション

### 2.1 期待する動作
- Tab で論理的な順序で移動: ヘッダー → 検索 → ナビ → 本文 → サイドバー → フッター
- Shift+Tab で逆順
- Enter / Space でボタン押下
- Esc でモーダル閉じ
- Arrow キーでドロップダウン項目選択

### 2.2 スキップリンク
本文先頭に「メインコンテンツへスキップ」リンクを配置:
```html
<a href="#main" class="skip-link">メインコンテンツへスキップ</a>
```
通常は視覚的に隠し、フォーカスで表示。

### 2.3 フォーカスインジケータ
- 全インタラクティブ要素にフォーカスリングを明示
- ブラウザデフォルト (`outline`) を消さない
- カスタマイズする場合は `outline: 2px solid #1976d2; outline-offset: 2px;` のような明確な視覚効果を維持

### 2.4 モーダル制御
- 開いた時に最初のフォーカス可能要素にフォーカス
- Tab がモーダル内をループ (フォーカストラップ)
- Esc で閉じ、開く前の要素にフォーカス復元

---

## 3. スクリーンリーダ対応

### 3.1 セマンティック HTML
- `<header>` / `<nav>` / `<main>` / `<aside>` / `<footer>` を適切に使用
- 見出しは `<h1>` から `<h6>` を階層順に
- ボタンとリンクを使い分け (`<button>` for action, `<a>` for navigation)

### 3.2 ARIA 属性の活用

```html
<!-- 申込ボタンの状態 -->
<button aria-pressed="false" aria-label="このイベントに申し込む">
  このイベントに申し込む
</button>

<!-- 動的に数値が更新される参加者数 -->
<div aria-live="polite" aria-atomic="true">
  参加者: <span>42</span> / 50 人
</div>

<!-- タブ UI -->
<div role="tablist">
  <button role="tab" aria-selected="true" aria-controls="panel-participants">参加者</button>
  <button role="tab" aria-selected="false" aria-controls="panel-waiting">補欠</button>
</div>
```

### 3.3 ランドマーク
```html
<header role="banner">
<nav role="navigation" aria-label="メインナビゲーション">
<main role="main" id="main">
<aside role="complementary" aria-label="関連イベント">
<footer role="contentinfo">
```

### 3.4 動的更新の通知
- 申込ボタンを押した後の「申込完了」メッセージは `aria-live="polite"` で通知
- 即座に通知すべきエラーは `aria-live="assertive"`

## 4. コントラスト比

WCAG AA は通常テキスト 4.5:1、大きいテキスト 3:1。

### 4.1 確認すべき箇所
- ヘッダーの薄いグレー文字
- フッターの濃緑背景に白文字
- イベントカードのキャッチコピー
- フォーム入力欄のプレースホルダー
- 「補欠」「定員に達しています」などのバッジ
- リンクの未訪問 / 訪問済み色

### 4.2 推奨カラーパレット
- 本文: #1a1a1a on #ffffff (21:1 → AAA)
- 補助テキスト: #555555 on #ffffff (7:1 → AAA)
- リンク: #1976d2 on #ffffff (5.6:1 → AA)
- 警告: #c62828 on #ffffff (6.4:1 → AA)
- 成功: #2e7d32 on #ffffff (4.6:1 → AA)

### 4.3 ダークモード対応
- prefers-color-scheme: dark で全体色相を反転
- ロゴ / アイコンが暗背景でも視認できるように

## 5. フォーム

### 5.1 ラベル
- すべての入力に `<label for="...">` または `aria-labelledby`
- プレースホルダーをラベル代わりにしない
- 必須項目に視覚 + テキスト両方で明示 (例: `* (必須)`)

### 5.2 エラー表示
```html
<div role="alert" aria-live="assertive">
  <h2>3 件のエラーがあります</h2>
  <ul>
    <li><a href="#email">メールアドレスは必須です</a></li>
    <li><a href="#password">パスワードは 8 文字以上にしてください</a></li>
    <li><a href="#nickname">ニックネームは既に使用されています</a></li>
  </ul>
</div>
```

### 5.3 入力支援
- `autocomplete` 属性で OS の入力履歴を活用
- `inputmode="email"` などでモバイルキーボード最適化
- パスワード可視化トグルボタン

## 6. 画像とメディア

### 6.1 alt 属性ガイドライン
| 画像種別 | alt の指針 |
|---|---|
| イベントカバー画像 | イベントタイトルそのもの (説明的) |
| ユーザーアバター | ニックネーム名 |
| グループアイコン | グループ名 |
| 装飾用 (区切り線、背景) | alt="" (空文字で明示的にスキップ) |
| アイコンボタン | aria-label でアクション名 |

### 6.2 動画 / 音声
- イベント詳細に埋め込まれた YouTube などは YouTube 側のキャプション機能に依存
- connpass 自身は埋め込み iframe に title 属性

---

## 7. ズームと文字サイズ

- ブラウザ 200% ズームでも要素が破綻しないこと
- 文字サイズの最小: 14px (本文)、12px (補助)
- rem 単位で指定し、ユーザー設定を尊重
- 横スクロールが発生しない (320px の幅でレイアウト崩れなし)

---

## 8. 動的コンテンツ

### 8.1 タイマー / カウントダウン
- 申込締切までの「あと N 日」表示
- スクリーンリーダで読み上げ過剰にならないよう aria-live="off" を基本に
- 重要な変化のみ aria-live="polite"

### 8.2 無限スクロール / ページネーション
- 無限スクロールは SR ユーザーに不親切
- 「もっと見る」ボタン + ページネーションが推奨

### 8.3 タブ / アコーディオン
- WAI-ARIA Authoring Practices のパターンに準拠
- Arrow キー、Home / End キー対応

---

## 9. モバイル特有のアクセシビリティ

- タップ領域 44×44px 以上 (Apple HIG / WCAG)
- スワイプジェスチャの代替操作
- iOS VoiceOver / Android TalkBack でのテスト

---

## 10. 多言語と読み上げ

- `<html lang="ja">` 必須
- 英語の引用は `<span lang="en">...</span>` で囲む
- ふりがな (ruby) を専門用語に付与する余地あり

---

## 11. アクセシビリティオーディット項目

開発時のチェックリスト:

- [ ] ページが Lighthouse Accessibility スコア 95+ である
- [ ] axe DevTools で重大な違反がない
- [ ] WAVE で構造エラーがない
- [ ] スクリーンリーダ (NVDA / VoiceOver) で全機能を操作できる
- [ ] キーボードのみで申込フローを完遂できる
- [ ] コントラストチェッカーで全テキストが AA 以上
- [ ] 200% ズームでレイアウト崩れなし
- [ ] prefers-reduced-motion ON でアニメーション抑制
- [ ] フォームエラー時に SR が読み上げる

---

## 12. 主催者ダッシュボードのアクセシビリティ

主催者向け UI は複雑なテーブルやドラッグ操作が増えるため、特別な配慮が必要:

### 12.1 参加者リストテーブル
- `<table>` に `<caption>`, `<thead>`, `<th scope="col">` を明示
- ソート可能列は `aria-sort="ascending|descending|none"`
- 出席チェックボックスに参加者名を含む aria-label

### 12.2 ドラッグ&ドロップ
- 参加枠の並び替えは矢印ボタン代替を提供
- ボタンに `aria-label="この枠を上へ移動"`

### 12.3 一斉メッセージ作成
- 送信前確認モーダルは role="dialog" aria-modal="true"
- 送信先カウントを aria-live で動的通知

---

## 13. アクセシビリティに関する不変条件

1. すべての画像に alt 属性が存在する (空文字含む)
2. すべてのフォーム要素にラベルが関連付けられている
3. クリック可能要素はキーボードでも操作できる
4. 色だけで情報を伝えない
5. フォーカスインジケータが必ず表示される
6. 動的に追加されるコンテンツは aria-live で通知される
7. ページ言語が `lang` 属性で宣言されている
8. 見出しレベルが論理順 (h1 → h2 → h3) で抜け飛びなし

## 17. 認識されている課題

connpass を観察した範囲での仮説:

- イベント詳細ページの「参加枠」「補欠」セクションがタブ UI ではなく単純なリスト表示の場合があり、関連情報の関連付けが弱い
- マイページの動的更新で SR ユーザーへの通知が抜けがち
- 抽選結果通知メールが HTML のみで、テキスト版がない可能性
- 出席コード入力フォームの SR フィードバックが不十分

---

## 18. アクセシビリティと SEO の重なり

- セマンティック HTML は両方の品質に寄与
- 構造化データ (Schema.org) は SR にもヒントを与える
- ページタイトルとメタディスクリプションは検索ユーザーと SR 双方に有益

## 20. メトリクス

- Lighthouse Accessibility スコア (CI で計測)
- axe-core 違反件数
- スクリーンリーダ実機テスト合格率
- アクセシビリティ問い合わせ件数 / 解決時間
- alt 属性カバレッジ (全画像に対する設定率)

これらを定期計測し改善サイクルを回すことで、connpass クローンとして実用的なアクセシビリティ水準を達成できる。
