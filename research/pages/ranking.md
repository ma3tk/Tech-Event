# ランキングページ

## 概要・目的

connpass の「人気イベントランキング」ページは、定期的（おそらく日次もしくは時間単位）に集計された「人気イベントトップ N」を一覧化したページである。connpass のサービス特性上、新着・直近開催イベントが多いため、ユーザーの興味から外れない範囲で「他のユーザーがいま注目しているイベント」を発見できるよう設計されている。

主な目的:

- 新着とは別軸での「話題のイベント」発見
- 主催者のモチベーション源（自分のイベントが何位かを意識）
- SEO 上の流入経路（外部からの検索でランキングページへ到達）
- イベント開催の社会的な賑わいの可視化

参考に閲覧した実例（`https://connpass.com/ranking/`）:

- タイトル: 「人気イベントランキング」
- 1 〜 50 位までの大きなランキングが表示
- 各エントリには「順位 / サムネ / 開催日 / ステータス / グループ名 / タイトル / 説明 / 主催者 / 開催場所 / 申込状況」が並ぶ
- 「2026 年 6 月 4 日 16 時 00 分 更新」のタイムスタンプあり
- 「<<前へ」リンクで前期間のランキングへ遷移
- はてブ / FB / X シェアあり

## URL 構造

- 最新ランキング: `https://connpass.com/ranking/`
- 過去ランキング: `https://connpass.com/ranking/?period={YYYY-MM-DD}` または `?page=2`
- 期間別ランキング (推測):
  - 日別: `?type=daily`
  - 週別: `?type=weekly`
  - 月別: `?type=monthly`
- カテゴリ別ランキング (推測): `?category=python`
- 主催者ランキング (推測): `https://connpass.com/ranking/organizer/`
- 発表者ランキング (推測): `https://connpass.com/ranking/presenter/`
- グループランキング (推測): `https://connpass.com/ranking/group/`

実例で確認できたのは「人気イベントランキング」のみ。主催者・発表者・グループの公式ランキングページが存在するかは未確認だが、「新着発表者」ページが存在することから、それに準じたランキングが用意される可能性は高い。

| 期間 / 集計タイプ | enum | 自動 | 日 / 週 / 月 |

| 順位リスト件数 | integer | 自動 | 50 件など |

| ラベル | データ型 | 備考 |

| 開催ステータス | enum | 「開催前」「終了」「中止」 |

| イベントタイトル | string + link | イベント詳細へ |
| 簡潔説明 (抜粋) | string | 100 文字程度 |
| 主催者アイコン | image | プロフィールへ |
| 主催者名 | string + link | 同上 |
| 開催場所 | string | 地名 or 「オンライン」 |
| 申込状況 | string | 「N / M 人」 |

## ランキングの集計軸（推測）

- **申込数**（参加 + 補欠 + 抽選を含む）
- **直近の急増率**（前回計測比の伸び）
- **ブックマーク数**
- **シェア数**（X / はてブ）
- **PV 数**
- **開催前イベントのみ集計**（過去イベントは別ランキング）

## 配置されている UI コンポーネント

- 期間切替タブ（日 / 週 / 月、または過去回への遷移）
- 「前へ / 次へ」ナビゲーション
- 更新日時バッジ
- シェアボタン群
- ランキングカード（順位 + サムネ + 詳細）
- カテゴリフィルタ（推測）
- 「順位推移」ミニグラフ（推測）

## 状態による出し分け

- **イベントが終了済 / 中止**: ステータスバッジで明示
- **満員**: 「定員到達」または「補欠枠あり」表示
- **抽選方式**: 「抽選中」ラベル
- **ブックマーク済**: ハートアイコンが塗りつぶし
- **未ログイン**: ブックマーク導線が「ログインしてブックマーク」になる
- **更新中**: 「ランキング更新中…」表示

## インタラクション

- カードクリックでイベント詳細へ
- 主催者アイコン / 名前クリックでプロフィールへ
- グループ名クリックでグループ詳細へ
- 「前へ / 次へ」で前回分のランキング閲覧
- シェアボタンで SNS 投稿
- カテゴリタブ切替で URL クエリ更新

## 推測される API コール

- `GET /api/v1/ranking/event/?period=daily` — 人気イベントランキング
- `GET /api/v1/ranking/event/?period=weekly&page=2`
- `GET /api/v1/ranking/group/?period=monthly` — グループランキング
- `GET /api/v1/ranking/presenter/` — 発表者ランキング
- バックエンドでは 1 時間ごとのバッチ集計 → キャッシュ配信が現実的

## 関連リンク・遷移先

- 各イベント詳細ページ
- 主催者プロフィール
- グループ詳細
- 新着イベント一覧
- 新着発表者一覧
- 新着グループ一覧
- フッターの「特集ページ」

## 模倣実装する際の留意点

- **集計頻度**: 1 時間ごと程度に再集計。リアルタイムは負荷が大きい
- **集計アルゴリズム**:
  - 単純な申込数ではなく「直近 24 時間の伸び率」を重視すると新陳代謝が促進される
  - 過剰な順位変動を抑えるため、順位の更新閾値を設ける（前回からスコアが N% 以上変化した場合のみ反映）
- **カテゴリの細分化**: 「人気イベント」「Python ランキング」「機械学習ランキング」「採用イベントランキング」など分割
- **公平性**: 大規模グループのイベントばかりが上位を占めないよう、定員と申込率の比、または小規模グループ用の別ランキングを設ける
- **個人情報配慮**: 主催者・発表者ランキングではプロフィール非公開のユーザーをスキップ
- **SEO 観点**: ランキングページは構造化データ (`ItemList`) を使うと Google での表示が改善
- **シェア最適化**: 「今週の人気イベントはこれ！」と OGP を動的生成
- **キャッシュ戦略**: CDN エッジキャッシュで広域配信、TTL を集計間隔に合わせる
- **ボット対策**: シェア数・PV 数を集計軸にする場合、ボットによる水増しを防ぐ
- **過去ランキングのアーカイブ**: 過去日付の URL でも永続的にアクセス可能に
- **マイランキング**: ユーザー自身の興味タグでパーソナライズしたランキング
- **メール配信**: 週次の人気イベントランキングメールはエンゲージメントに有効
- **アクセシビリティ**: 順位を文字でも明示（「1 位:」とテキスト併記）
- **ダークモード対応**: シェアバッジの視認性
- **モバイル UX**: 順位とタイトルを大きく、詳細は折りたたみ

## 派生ランキングの設計

### グループランキング（推測）

- 月次のメンバー増加数
- 開催イベント数
- 累計参加者数
- アクティブメンバー比率

### 主催者ランキング（推測）

- 主催イベント数
- 累計参加者
- リピート率
- 評価（アンケート集計）

### 発表者ランキング（推測）

- 発表回数
- 視聴・閲覧された資料数
- フォロワー数
- 発表後の参加者からのフィードバック

### カテゴリ別ランキング（推測）

- Python / 機械学習 / フロントエンド / モバイル / セキュリティ / インフラ / デザイン …

## 申込率（人気度）の計算式（推測）

```
人気スコア = (申込数 / 定員) * w1
            + 直近 24h 申込増加数 * w2
            + ブックマーク数 * w3
            + シェア数 * w4
            + PV 数 * w5
            - 中止 / キャンセル率 * w6
```

重み `w1〜w6` はチューニング項目。新陳代謝重視なら `w2` を大きく、安定性重視なら `w1` を大きく。

## ランキングの落とし穴

- 大規模グループのイベントばかりが上位を独占しがち
- 一度上位に乗ったイベントが慣性で居座りやすい
- 主催者によるブックマーク水増しの可能性
- 終了したイベントを含めるか否かで意味合いが変わる
- 「人気=参加したい人が多い」と「人気=注目されている」は別

## 改善アイデア

- 定員に対する充足率を上位指標に
- 新興グループ専用ランキングを別途
- 「あなたへのおすすめランキング」をパーソナライズ
- 「クリックしてから申込転換した率」を加味
- 集計式とパラメータの定期見直し

## API 提供の可能性

- 既存の connpass 公開 API v1 にはランキング API はない
- 開発者から見ると「人気イベントを取得したい」というニーズはあるため、`GET /api/v2/ranking/event/` のような公開 API を後付けで提供する余地あり
- レート制限 + キー必須

## バッチ集計の運用設計

- 1 時間ごとに過去 24 時間のスコアを再計算
- 計算済みのスコアを Redis ZSET に格納
- 表示時は ZSET からトップ N を取得 + 詳細を DB から JOIN
- ランキングの履歴を別テーブルに保存し、過去ランキング閲覧を可能に

## SEO 観点での追加項目

- ページタイトル: `人気イベントランキング | YYYY 年 MM 月 DD 日更新`
- canonical URL を最新版に固定
- 過去ランキングは noindex (薄いコンテンツ判定回避)
- 構造化データ ItemList の position プロパティで順位を明示
- パンくず（ホーム > ランキング > 人気イベント）

## 計測すべき指標

- ランキング経由の詳細ページへの遷移率
- ランキングページからの直帰率
- シェア数（ランキングページ自体の拡散）
- ユニークユーザー数 / 再訪率
- 各順位のクリック分布（1 位ばかりクリックされるか、満遍ないか）
