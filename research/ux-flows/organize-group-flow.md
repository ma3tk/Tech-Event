# グループ運営者の日常運用フロー

connpass のグループ管理者が、グループのライフサイクル全体を通じて行う日常的な運用業務を整理する。単発のイベント開催 (=create-event-flow.md で扱った) に対し、本書は「コミュニティとしての継続運営」の観点。

---

## 0. 全体像

グループ運営者の作業は「コミュニティの維持」「メンバーへの提供価値の最大化」「ブランド一貫性」の 3 軸。

```
[グループ設立]
  └─ コミュニティビジョン明確化 → 初期メンバー獲得 → 初回イベント

[運用フェーズ]
  ├─ 定期イベント企画・開催
  ├─ メンバー獲得施策 (告知、口コミ、コラボ)
  ├─ コミュニケーション (一斉メッセージ、コメント返信)
  ├─ コンテンツアーカイブ (発表資料、レポート)
  └─ 管理者ロール拡張 / 共同運営

[改善フェーズ]
  ├─ 統計確認、テーマ調整
  ├─ ブランディング刷新 (カバー画像、色、説明文)
  └─ ブラックリスト・トラブル対応

[終結フェーズ]
  └─ アーカイブ宣言、運営終了告知
```

---

## 1. グループ設立

(本書は「日常運用」が主題のため簡潔に)

- 「ヘッダー > イベント管理 > グループを作成する」から起動。
- グループ名、サブドメイン (変更不可) を決定。
- ブランディング: カバー画像、サムネイル、背景色、説明文 (Markdown)。
- 共同管理者 / 公式リンクを設定。

---

## 2. 初期メンバー獲得

connpass はメンバー数がコミュニティの活発度を可視化するため、初期段階での獲得が重要。

### 2.1 自然流入チャネル
- 初回イベントを公開 → 申込者が自動メンバー化 (joined_via=event_join)
- グループページの URL をシェア → 「メンバーになる」ボタンで手動加入
- グループ管理者の SNS フォロワー → 告知拡散

### 2.2 一括追加
- CSV/TSV 形式で「名前, メールアドレス」を入力して一括登録
- 既存ユーザーがメールアドレスで突き合わさり、未登録なら新規招待メール
- joined_via=admin_add で記録

### 2.3 提携・コラボ
- 別グループの管理者と共催イベント → メンバー相互流入

---

## 3. 継続的なイベント企画

### 3.1 開催ペース
- 月次・隔月・季節など、コミュニティのテーマに合わせる
- カンファレンス特集機能 (`Event.parent_event_id`) で年次イベントを構造化

### 3.2 イベントカレンダー管理
- 「イベント管理」画面で公開予定・募集中・終了を俯瞰
- 重複日時を避けるための内部カレンダー
- 編集権限のある共同管理者間で進行状況を共有

### 3.3 テンプレート活用
- ヘルプ「イベントをコピーして新しく作成する」機能あり
- 過去イベントを複製 → 日時 / 説明を差し替えて公開
- 参加枠構成 (一般 / LT / 学生) を使い回す

### 3.4 サブイベントの活用
- 大規模カンファレンスは親イベント + 子セッションで構造化
- 「サブイベントを作成する」ヘルプ通り、親イベントに紐づける

---

## 4. メンバーコミュニケーション

### 4.1 一斉メッセージ
- 件名 / 本文を作成
- audience を選択: 「グループメンバー全員」「特定イベントの申込者」など
- 配信前のプレビュー、送信先カウント確認
- 履歴は Message テーブルに保存

### 4.2 イベントページのコメント返信
- 参加者からの質問にコメントで返答
- 主催者コメントはピン留め (`Comment.is_pinned`) で目立たせる
- スレッド形式でやり取り (`parent_comment_id`)

### 4.3 SNS 連携
- グループ公式 X アカウントへの自動投稿
- ハッシュタグキャンペーン
- イベントレポート公開

---

## 5. コンテンツアーカイブ

### 5.1 発表資料
- 開催後速やかに PresentationMaterial を登録
- 発表者ごとにタイトル + URL (Speaker Deck / SlideShare / GitHub)
- グループページの「資料」セクションに累積表示 (例: Findy 905 件, LayerX 194 件)

### 5.2 イベントレポート
- 説明欄にイベント後にレポートリンクを追記
- togetter / note の URL を貼る

### 5.3 録画動画
- YouTube / niconico の埋め込みリンク

---

## 6. ブラックリスト管理

### 6.1 利用シーン
- 重複アカウントによる不正申込
- ハラスメントや規約違反
- 連続キャンセル等の迷惑行為

### 6.2 追加手順
- グループ設定 > ブラックリスト > ユーザー指定
- 理由 (reason) を内部メモとして記録
- 追加時に AuditLog に記録

### 6.3 結果
- ブラックリストユーザーは配下イベントへの申込不可
- グループメンバー / 申込履歴は強制的にキャンセル
- 通知設定もオフ

---

## 7. 統計確認と改善

### 7.1 グループ統計
- メンバー数推移
- 各イベントの参加者数 / 出席率
- 累積発表資料数
- メールマガジン (告知) のクリック率

### 7.2 イベント統計 (EventStat)
- PV / UU
- 申込数 / キャンセル数
- 補欠率
- 出席率
- アンケート回答率

### 7.3 改善アクション
- 出席率が低ければ会場アクセス改善・リマインダー強化
- 申込率が低ければタイトル / 説明文の見直し
- キャンセル率が高ければ開催曜日変更や事前決済導入

---

## 8. 共同運営とロール拡張

### 8.1 管理者追加
- 編集ページでユーザー名検索 → 候補から選択
- 同等の編集権限を付与
- 役割分担 (例: A はイベント企画、B は当日受付、C はコンテンツ管理)

### 8.2 引き継ぎ
- 既存管理者の退任時は、後任管理者を追加してから自身を削除

### 8.3 owner / admin の役割差
- owner: グループ削除 / ブラックリスト全権
- admin: イベント・メッセージ・ページ編集

---

## 9. ブランディング刷新

定期的にグループの「鮮度」を維持する施策。

- カバー画像の刷新 (季節 / 新シリーズ告知)
- サブタイトルの更新 (例: 「2026 年は AI Agent シリーズ」)
- 説明文の Markdown を改稿
- 背景色 (背景は配下イベントにも反映)

---

## 10. グループのアーカイブ / 終結

### 10.1 終了告知
- 説明文の冒頭に「このグループは XXXX 年 N 月をもって活動を終了しました」と追記
- 最終イベントを開催

### 10.2 削除
- メンバーやイベントを持つグループは削除不可 (FAQ)
- 削除したい場合は connpass 運営に申請

### 10.3 アーカイブステータス
- `Group.status=archived` (本クローンの設計案)
- 新規イベント作成を不可
- ページは閲覧のみ可能

---

## 11. 日常運用カレンダー (例)

| 周期 | 業務 |
|---|---|
| 毎日 | コメント返信、申込状況の確認 |
| 毎週 | 統計確認、次回イベントの企画 |
| 隔週 | 一斉メッセージ送信 (テーマ / 告知) |
| 月次 | イベント開催、振り返り、レポート公開 |
| 四半期 | カバー画像 / 説明文の刷新 |
| 半年 | 共同管理者ローテーション、KPI レビュー |
| 年次 | カンファレンス開催、コミュニティ方針決定 |

---

## 12. UI / UX ベストプラクティス (運営者向け)

### 12.1 ダッシュボードの構造
- グループ別タブ
- 今日のタスク (未対応コメント、申込中のイベント)
- 申込急増アラート (PV/申込が急増したイベント)

### 12.2 通知集約
- 主催イベントの新着コメントを在App通知 / Slack 連携で集約
- メール通知 ON/OFF をきめ細かく設定

### 12.3 メンバー検索
- 名前 / メアド / 参加履歴で検索
- セグメント別エクスポート (CSV)

## 14. トラブルシューティング

### 14.1 メンバーから「メールが届かない」
- ユーザー側の通知設定 (`receive_notification_email`) を確認
- 受信側ドメインのスパム判定を疑う (DMARC / SPF / DKIM の設定確認)
- メール再配信機能を提供する

### 14.2 イベント当日のシステム障害
- 出席コードのバックアップ取得 (CSV)
- 紙の名簿 (PDF) の事前出力推奨

### 14.3 不正アカウントの大量申込
- ブラックリスト + 強制キャンセル
- AuditLog の `participant.apply` から短時間で同一 IP の連続申込を抽出
- 必要に応じ connpass 運営へ報告

## 15. KPI / 健康指標

グループ運営の KPI:

| 指標 | 計算式 | 目標値の目安 |
|---|---|---|
| メンバー増加率 | (今月メンバー数 - 先月) / 先月 | +5% / 月 |
| イベント開催頻度 | 月あたり開催数 | 1〜4 回 |
| 平均出席率 | sum(attended) / sum(accepted) | 70% 以上 |
| リピート参加率 | 参加者のうち過去にも参加したユーザー比率 | 40% 以上 |
| 資料公開率 | 開催イベントのうち資料 1 件以上登録された比率 | 80% 以上 |
| コメント応答率 | 主催者が 24h 以内に返信したコメント比率 | 90% 以上 |
| メールクリック率 | 一斉メッセージのクリック / 送信 | 5% 以上 |

これらを月次ダッシュボードで運営チームに共有し、改善サイクルを回す。

## 16. ガバナンスと規約

### 16.1 コミュニティガイドライン
- 主催グループ独自のガイドラインを説明文に明記
- 行動規範 (CoC) の URL リンク
- 禁止事項 (商用営業のみの参加など)

### 16.2 個人情報の扱い
- CSV エクスポートしたメールアドレスの取り扱い注意
- 退会者のメールアドレスは速やかに破棄
- 主催者は自己の責任で個人情報保護法を遵守

### 16.3 連絡先
- グループ説明文に問い合わせ先を明記
- イベント中止時の連絡フロー (一斉メッセージ + SNS)

---

## 17. 終了基準とアーカイブ宣言

グループ運営の終了が見えた時:

1. 主要管理者で合意
2. 最終イベントを開催 (思い出共有会など)
3. グループ説明文に「N 月 N 日をもって活動を終了します」と明記
4. アーカイブ後の問い合わせ先を表示
5. Group.status を `archived` に更新

ヘルプ FAQ にも「グループのページに、活動が終了している旨を一言入れていただけますと、過去のメンバーや、これから検索してアクセスしてきたユーザーにも親切」とある。
